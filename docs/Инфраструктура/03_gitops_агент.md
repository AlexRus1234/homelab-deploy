
# GitOps-агент: Pull-модель и Автоматизация (Webhook)

Механизм автоматизации состоит из двух компонентов: **сервера Webhook** и **Bash-скрипта синхронизации**.

## 1. Слушатель событий (Webhook)
На каждой виртуальной машине (хосте контейнеров) запущен бинарный файл `adnanh/webhook` в качестве системной службы.

*   **Функция:** Ожидание POST-запросов от центрального сервера Forgejo.
*   **Безопасность:** Запрос обрабатывается только в том случае, если HTTP-заголовок `X-Gitea-Signature` содержит корректную криптографическую подпись (HMAC SHA-256), совпадающую с локальным секретным ключом. Это исключает несанкционированный запуск обновлений.
*   **Действие:** При получении валидного сигнала (Push Event в ветку `main`), сервер выполняет локальный скрипт `sync-state.sh`.

## 2. Изоляция контекста (Sparse-Checkout)
Так как все конфигурации для всех виртуальных машин хранятся в едином монорепозитории (`homelab-deploy`), клонирование всего репозитория на каждый хост является небезопасным и избыточным.

Используется функционал Git **Sparse-Checkout** (современный режим `--sparse`):
```bash
# Пример для ВМ obshaga (yadr00)
git clone --filter=blob:none --sparse https://git.yadr00.internal/AlexRus1234/homelab-deploy.git /opt/appdata/git-repo
cd /opt/appdata/git-repo
git sparse-checkout set servers/yadr00/obshaga
```
Для ВМ `panelka` вместо пути указывается `servers/yadr01/panelka`. ВМ загружает только ту директорию, которая относится к ней — ВМ «Общежитие» физически не имеет доступа к пайплайнам или конфигурациям ВМ «Панелька».

## 3. Логика работы `sync-state.sh`
Скрипт синхронизации написан с учетом идеологии идемпотентности (многократный запуск приводит к одному и тому же правильному результату).

### 3.1. Синхронизация с Git
```bash
git pull origin main
```
Скрипт подтягивает актуальное состояние ветки `main` в локальную копию репозитория. Перед и после `pull` фиксируются хеши коммита (`OLD_HASH` / `NEW_HASH`) — они используются на последующих этапах для вычисления удалённых и изменённых файлов. При отсутствии изменений скрипт завершает работу досрочно после `podman auto-update`.

Защитные меры:
*   Перед pull скрипт выполняет `git config core.fileMode false` — разница бит исполнения между репозиторием и ВМ (ручной chmod) больше не делает дерево «грязным» и не блокирует pull ошибкой `Your local changes would be overwritten by merge`.
*   Если `git pull` завершился с ошибкой, скрипт **прерывается с ненулевым кодом выхода** — webhook вернёт `500`, и сбой будет виден в логах Forgejo, вместо молчаливого «Изменений не найдено» при залипшем HEAD.

### 3.2. Обработка удалений (Очистка)
```bash
DELETED_FILES=$(git diff --name-only --diff-filter=D $OLD_HASH $NEW_HASH ...)
```
Перед применением новых конфигураций скрипт анализирует удаленные файлы. Если `.container` файл был удален или переименован в Git, скрипт **останавливает** (`systemctl stop`) соответствующую системную службу до того, как удалит конфигурацию. Это предотвращает возникновение служб-призраков с зависшими сетевыми портами.

### 3.3. Зеркалирование (Rsync)
Для переноса файлов из скачанного репозитория в системные папки Podman используется `rsync`.
*   **Папка Quadlets (`--delete`):** `rsync -rlptD --delete`. Гарантирует, что папка `~/.config/containers/systemd/` становится точной копией репозитория. Весь мусор удаляется.
*   **Папка App-Configs (Без удаления):** `rsync -rlptD`. Конфиги копируются **без** ключа `--delete`. Это критически важно, так как в целевой папке на ВМ находятся "боевые" `.env` файлы с реальными паролями, которых нет в Git-репозитории.

### 3.4. Запуск сетевых юнитов (`.network`)

После `daemon-reload` скрипт выполняет `systemctl --user start` для **всех служб, сгенерированных из `*.network`** quadlet-файлов. Без этого шага новую сеть никто бы не поднял: systemd не стартует добавленный юнит сам по себе, а `Requires` от контейнеров срабатывает только при их собственном рестарте. Старт идемпотентен — для уже запущенной сети это no-op (`podman network create --ignore`).

### 3.5. Обновление образов (Podman Auto-Update)
```bash
podman auto-update
```
Скрипт дает команду демону Podman проверить локальный реестр образов. Если для контейнеров (у которых прописан флаг `AutoUpdate=registry`) появилась новая сборка с тегом `:latest`, Podman самостоятельно скачивает слои, останавливает контейнер и перезапускает его на новом образе.

Команда запускается **двумя независимыми путями** (см. [`заметки/podman/01-автообновление.md`](../заметки/podman/01-автообновление.md)):
1.  **По пушу** — из `sync-state.sh` (строки 20 и 59): образы, собранные вместе с изменением конфигурации.
2.  **По расписанию** — systemd-таймер `podman-auto-update.timer` (user-юнит, override в окне 03:00–04:00): образы, пересобранные в реестре без пуша в этот репозиторий (например, обновление базового образа в CI). Настройка — [`06_настройка_ВМ.md`](06_настройка_ВМ.md), этап 2.4.

### 3.6. Перезапуск служб (гибридная логика)
```bash
CHANGED_FILES=$(git diff --name-only --diff-filter=AM $OLD_HASH $NEW_HASH ... | grep '\.container$')
```
По умолчанию скрипт анализирует только изменённые или добавленные (`--diff-filter=AM`) Quadlet-файлы и выполняет `systemctl restart` **точечно**, минимизируя даунтайм сервисов. Неизменённые контейнеры не затрагиваются.

Для случаев, когда требуется гарантированно перезапустить все службы (например, после изменения структуры каталогов, правок самого `sync-state.sh` или обновления общих образов), предусмотрен **принудительный полный перезапуск** через переменную окружения:
```bash
FORCE_FULL_RESTART=1 /opt/appdata/git-repo/.../sync-state.sh
```
При `FORCE_FULL_RESTART=1` скрипт проходит по всем `~/.config/containers/systemd/*.container` и перезапускает каждую службу. По умолчанию (`FORCE_FULL_RESTART` не задан или `0`) применяется точечный режим.

## 4. Узел без ВМ (skld00): тот же агент, применяет Incus

Bare-metal узел `skld00` (NAS + Incus-склад образов) использует **тот же механизм** — `adnanh/webhook`
+ `sync-state.sh` + sparse-checkout, отличие только в том, что применяется не rootless Podman,
а Incus. Порт агента на skld00 — `9002` (конвенционный `9000` там занят RustFS, S3-хранилищем Forgejo).

| | ВМ (`obshaga`/`panelka`) | `skld00` |
| :--- | :--- | :--- |
| Sparse-checkout | `servers/<узел>/<вм>` | `servers/skld00` |
| Что применяется | `quadlets/` → `~/.config/containers/systemd/`, `app-configs/` → `/opt/appdata/config/` | `services/*.yaml` → инстансы Incus: `create` → `start` → cloud-init (пакет + `enable`) → чтение uid → `chown 100000+uid` датасета → `systemctl start` юнита → проба; смена состава → пересоздание с откатом (см. 4.1) |
| Агент | `app-runner`, юнит `systemd --user` | `root`, системный юнит `webhook.service` |
| Хук | `sync-<вм>` | `sync-skld00` |

`sync-state.sh` узла делает `git pull`, сравнивает хеши по своему поддереву и при изменениях вызывает
`reconcile.sh` (перечисление/применение деклараций). Описание узла — `servers/skld00/README.md`,
формат деклараций — `servers/skld00/services/README.md`.

Почему на skld00 агент под `root`, а не от unprivileged-пользователя: на ВМ `app-runner` оправдан
rootless Podman'ом, который привилегий не требует; здесь полезная нагрузка — Incus и ZFS, где `incus-admin`
уже эквивалентен root, а работа с датасетами (`zfs`, монтирования, shifting) требует root напрямую.

### 4.1. Пересоздание инстанса (правка состава) и откат

Правка состава декларации (`devices`, `cloud-init.user-data`, `raw.idmap`) живьём невозможна —
меняется корневая файловая система и карта uid. Контур делает это пересозданием:

```
zfs snapshot <датасет>@recreate-<дата>
incus stop <имя> && incus rename <имя> <имя>-pre-<дата>     # старый НЕ удаляется
create по новой декларации → start → cloud-init → uid → chown → systemctl start → проба
успех: applied обновлён, <имя>-pre-<дата> ждёт GC
провал: delete нового → rename старого обратно → zfs rollback → start → проба
```

Ключевое решение: **откат опирается на сам инстанс, а не на старую декларацию.** Пересобрать по
предыдущей декларации из git нельзя гарантировать: обновление могло подтянуть другую базу, версия
пакета могла уехать из Хражевника — и откат не соберётся как раз тогда, когда нужен. `rename`
на zfs не копирует данные, поэтому отставленный инстанс хранит ровно те пакеты и конфиги, что
работали. Git-декларация остаётся третьим эшелоном (бесплатным), но не основой отката.

Ручной режим (пересобрать инстанс, когда декларация не менялась — например, он остался в отладочном
состоянии):

```sh
sudo /opt/appdata/git-repo/servers/skld00/reconcile.sh --recreate vl1
```

Ночное обновление пакетов и уборка снапшотов/стоянок — отдельная часть контура (`update.sh` +
таймер `lxc-update.timer`), см. 4.3. Общие для обоих скриптов части (разбор деклараций, карта uid,
отчёт) вынесены в `servers/skld00/lib.sh`.

### 4.2. Снятие: декларация исчезла из git

Как и на ВМ (`3.2`: `--diff-filter=D` + `systemctl stop` + `rsync --delete`), удаление декларации в
git означает снятие сервиса на узле — но только с маркером `user.managed-by: homelab-deploy/skld00`
(у Incus нет «своей папки», по которой видно принадлежность, поэтому принадлежность объявлена явно).
Перед снятием снимается снапшот датасета с данными; сам датасет не удаляется — данные и «сервис
больше не нужен» это два разных решения. Восстановление — git revert + push.

### 4.3. Ночное обновление пакетов и уборка (`update.sh`)

Вторая половина контура узла: `reconcile.sh` приводит инстансы к декларациям, `update.sh` обновляет в
них пакеты и убирает старое. Общие части обоих скриптов (разбор деклараций, карта uid, отчёт, метки
времени) лежат в `servers/skld00/lib.sh` — одна реализация на два скрипта.

Запуск — таймер `lxc-update.timer` (юниты в `servers/skld00/systemd/`): `OnCalendar=*-*-* 02:00:00` +
`RandomizedDelaySec=3600`, то есть окно **02:00–03:00 по местному времени узла**, и прогон встаёт в
случайный момент внутри часа (у узлов парка окна не совпадают). `Persistent=true` — прогон не теряется,
если узел был выключен в окно. Руками: без аргументов (обновить все `inplace` + уборка), `--gc-only`,
`--one <имя>`, `--dry-run`; флаг `/etc/lxc-automation.off` тоже оставляет только план.

Порядок по сервису с `user.update_policy: inplace`:

```
incus snapshot create <имя> pre-<дата>  +  zfs snapshot <датасет>@pre-<дата>
флаг /var/lib/lxc-update.pending ВНУТРИ инстанса
zypper --non-interactive dup → incus restart → маркер загрузки обновился (mtime ≥ эталона)
systemctl is-system-running → проба user.healthcheck (повторы) → флаг снят, статус «ok»
провал: stop → incus snapshot restore <имя> pre-<дата> → zfs rollback -r <датасет>@pre-<дата> → start → проба
```

Три решения, которые здесь важнее кода:

- **флаг внутри инстанса держит инвариант «нет флага — нет сомнений».** Он ставится до `zypper` и
  снимается только после зелёной пробы; флаг, найденный на старте (прошлый прогон умер: питание,
  зависание), уводит сервис сразу в откат, а не оставляет обновление, которое никто не проверял;
- **свежесть маркера загрузки, а не «RUNNING»**: RUNNING не доказывает, что инстанс перезапустился,
  а `mtime` маркера ≥ эталона (он берётся до снапшота) — доказывает;
- **откат — снапшотом самого инстанса**, не пересборкой по старой декларации: та же логика, что в 4.1.
  Если не помог и он — флаг остаётся, в статусе «ОТКАТ НЕ ПОМОГ — нужен человек», прогон возвращает
  ненулевой код.

Уборка (GC) снимает только наши объекты (`pre-*` у инстанса, `@pre-`/`@update-`/`@recreate-`/`@removed-`
у датасета, стоянки `<имя>-pre-<дата>`) и только у доказанно живого сервиса: инстанс `RUNNING` и серия
успешных проб ≥ 3 (`/var/lib/lxc-health.streak` внутри), возраст объекта ≥ `user.rollback_window`
(базово `24h`) и объект не входит в N=3 самых свежих. Если живость не доказана — не чистится ничего,
в отчёт идёт причина. Датасет данных не удаляется никогда.

Сервисы с `user.update_policy: recreate` ночной контур не трогает: их обновление — пересоздание
(`reconcile.sh --recreate <имя>`), то есть решение человека, а не таймера; в отчёт пишется «пропуск».

Отчёт — `/var/lib/lxc-update/status` (и journal юнита), метрики для node_exporter — `lxc.prom` в
каталоге textfile-коллектора: `lxc_instance_health`, `lxc_health_streak`,
`lxc_last_update_success_timestamp`, `lxc_rollback_total`, `lxc_snapshots_deleted_total`. Обновление и
применение деклараций идут по одному замку (`/var/lib/lxc-update/.lock`) — одновременно они не работают.
