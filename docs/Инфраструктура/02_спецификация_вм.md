# Спецификация Виртуальных Машин (Pets)

Этот документ описывает единый аппаратный и системный стандарт для создания виртуальных машин-хостов (например, `obshaga` и `panelka`), предназначенных для запуска Rootless Podman контейнеров. 

Система построена на принципах **Stateless** (инфраструктура без состояния): операционная система является расходным материалом, а все критичные данные вынесены на отдельный виртуальный диск.

## 1. Аппаратная конфигурация (Proxmox VE)

Создание ВМ производится путем  клонирования (Full Clone) из подготовленного базового шаблона Arch Linux.

*   **ОС:** Arch Linux (минимальная серверная установка).
*   **System:** Q35, QEMU Guest Agent (Enabled), BIOS (SeaBIOS).
*   **CPU:** 3-6 Cores 
*   **RAM:** 8192 MB (8 GB). Баллунинг отключен.
*   **Network:** Адаптер VirtIO, подключен к `vmbr0`, если есть`vmbr1`

## 2. Архитектура дисковой подсистемы

Для обеспечения  легкого резервного копирования и быстрого восстановления при сбоях ОС, ВМ разделяется на два виртуальных SCSI-диска (обязательно с включенными флагами `SSD emulation` и `Discard`).

| Диск | Размер | Файловая система | Точка монтирования | Назначение | Политика Бэкапа |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **sda (OS)** | 12 GB | Btrfs / ext4 | `/` (Корень) | ОС, бинарники, слои и кэши образов Podman, локальная копия Git-репозитория. |  (Расходник) |
| **sdb (Data)** | 1 GB | ext4 | `/opt/appdata/db` | Базы данных (SQLite, WAL), токены авторизации (htpasswd) и пользовательские файлы. | **Ежедневный инкрементный бэкап** |

### 2.1 Оптимизация диска Data
Диск `/opt/appdata/db` монтируется через `/etc/fstab` с обязательным флагом `noatime`.
`UUID=... /opt/appdata/db ext4 defaults,noatime,discard 0 2`
Отключение записи времени последнего доступа к файлу критически снижает износ диска и повышает производительность IOPS, что необходимо для стабильной работы баз данных (например, SQLite для сервиса Memos) внутри контейнеров.

## 3. Права доступа и Безопасность

### 3.1 Пользователь-сервис
В операционной системе запрещен запуск контейнеров от имени пользователя `root`. Для работы служб создан отдельный системный пользователь:
*   **Имя:** `app-runner`
*   **Особенности:** Для пользователя включена служба длительной фоновой активности (`loginctl enable-linger app-runner`), что позволяет Systemd управлять контейнерами даже после закрытия SSH-сессии.
*   **Владение:** Пользователь имеет полные права (`chown -R`) на рабочую директорию `/opt/appdata`.

### 3.2 Доверенные сертификаты (PKI)
Для того чтобы Podman мог безопасно скачивать образы OCI из локального защищенного реестра (Forgejo Registry), в систему импортирован корневой сертификат локального удостоверяющего центра.
Сертификат `step-ca.crt` скопирован в `/etc/ca-certificates/trust-source/anchors/` и применен командой `update-ca-trust`. Без этого шага Podman блокирует загрузку образов по HTTPS.

## 4. Размещение конфигураций (GitOps)

Папка с конфигурациями контейнеров (`/opt/appdata/config`) физически располагается на системном диске `sda` (12 GB) и имеет следующую структуру:
*   **`/opt/appdata/config/quadlets/`** — Quadlet-файлы (`.container`). Синхронизируются с центральным Git-репозиторием агентом (`webhook` + `sync-state.sh`) и линкуются симлинком в `~/.config/containers/systemd/` для чтения systemd.
*   **`/opt/appdata/config/<service>/`** — конфиги приложений и локальные `.env` файлы (например, `/opt/appdata/config/athens/athens.env`). Синхронизируются через `rsync` **без** `--delete`, поэтому боевые `.env` с паролями не затираются.
*   **Секреты:** Файлы переменных среды (например, пароли от S3) создаются вручную на системном диске сервера и не подлежат загрузке в Git (защищены `.gitignore`: `*.env` игнорируются, `*.env.example` остаются в репозитории как шаблоны).

В случае утраты системного диска `sda`, виртуальная машина воссоздается из шаблона, к ней подключается сохраненный диск `sdb` (Data), восстанавливаются `.env` файлы, после чего запускается скрипт GitOps-синхронизации, который автоматически загружает Quadlet-файлы и запускает контейнеры.
