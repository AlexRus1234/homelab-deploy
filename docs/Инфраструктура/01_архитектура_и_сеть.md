# Архитектура и Сетевая Топология

Данный документ описывает общую архитектуру домашнего дата-центра (HomeLab), схему взаимодействия узлов

## 1. Общая топология узлов

В инфраструктуре задействованы логические и физические узлы, выполняющие строго разделенные функции.

### 1.1. SHLZ00 (Шлюз / Маршрутизатор)
*   **Роль:** Главный шлюз, DNS-сервер и Reverse Proxy домашней сети.
*   **ОС:** Arch Linux (на базе специализированного мини-ПК с многопортовой сетью).
*   **Сервисы:** Firewall (nftables), DNS (Unbound/Dnsmasq), Step-CA (удостоверяющий центр, выдаёт TLS-сертификаты для локальных сервисов; корневый сертификат раздаётся по `http://172.20.0.1:9000/roots.pem`).
*   **Функция:** Терминирует входящий трафик, управляет маршрутизацией, выдает локальные доменные имена (например, `*.yadr00.internal`) и проксирует запросы на нужные порты виртуальных машин.

### 1.2. SKLD00 (NAS / СХД)
*   **Роль:** Центральное хранилище данных и СУБД.
*   **Сервисы:** PostgreSQL, RUSTFS (S3-совместимое объектное хранилище).
*   **Сеть:** Подключен к общей сети маршрутизатора (LAN) и имеет выделенный сетевой интерфейс для прямого соединения с узлом `YADR01`. S3-endpoint RUSTFS доступен на P2P-линке по адресу `172.21.6.249:9000`.

### 1.3. YADR00 -> ВМ `obshaga`
*   **Роль:** Вычислительный узел для легковесных пользовательских приложений.
*   **ОС:** Arch Linux (минимальная установка).
*   **Сеть:** Подключена к общей сети (`vmbr0`). Доступ к сервисам возможен как через прокси (доменное имя), так и напрямую по IP ВМ и открытому порту.
*   **Размещенные сервисы:** 
    *   Dashy (Стартовый дашборд)
    *   LinkStack (Мультиссылки)
    *   Memos (Заметки)
    *   Webhook (Агент GitOps-синхронизации)

### 1.4. YADR01 -> ВМ `panelka`
*   **Роль:** Инфраструктурный вычислительный узел. Обрабатывает тяжелый  трафик 
*   **ОС:** Arch Linux (минимальная установка).
*   **Сеть:** Имеет два сетевых интерфейса:
    1.  Подключение к общей сети (`vmbr0`) для управления и приема входящих запросов.
    2.  Прямой L2-линк (Point-to-Point) до узла `SKLD00` (`vmbr1`) с пропускной способностью 2.5G.
*   **Размещенные сервисы:**
    *   NORA (Pull-through кэш-прокси для npm, go, oci-образов).  
    *   Webhook (Агент GitOps-синхронизации)
*   **Обоснование архитектуры:** Кэширование слоев Docker-образов и языковых пакетов генерирует массированный трафик между прокси-сервером и S3-хранилищем. Размещение сервиса NORA на ВМ `panelka` позволяет направить этот трафик по выделенному аппаратному линку напрямую в NAS, полностью исключая нагрузку на основной коммутатор домашней сети.

### 1.5. LXC-контейнеры (вспомогательные сервисы)
На узлах `YADRXX` помимо ВМ разворачиваются легковесные LXC-контейнеры под вспомогательные сервисы, не вписывающиеся в модель Rootless Podman. Управляются они отдельными workflow (`yadr01-deploy-caddy.yml`, `yadr01-deploy-sftpgo.yml`) по SSH от пользователя `root` и используют общий секрет `SSH_PRIVATE_KEY` (в отличие от ВМ-деплоев с гранулярными ключами).

*   **Caddy** — Reverse Proxy. Живёт в собственном LXC на каждом узле `YADRXX` (своё инстанс на узел). Конфигурация (`Caddyfile`) поддерживается внутри LXC и в данный момент в репозиторий не выкладывается (`system-templates/caddy/Caddyfile.template` зарезервирован пустым).
*   **SFTPGo** — SFTP/FTP-сервер, LXC на `YADR01`.

> Примечание: детальная конфигурация Caddy (правила проброса доменов) в рамках данного документа не описывается — см. отдельный LXC-инстанс.

Внутри виртуальных машин все приложения запускаются от бесправного пользователя (`app-runner`). По соображениям безопасности и во избежание конфликтов портов на хосте, все опубликованные порты (`PublishPort`) вынесены в нестандартный диапазон `10000+`. Нумерация портов ведется независимо для каждой виртуальной машины.

| Сервис | Внутренний порт | Опубликованный порт | Описание |
| :--- | :--- | :--- | :--- |
| Webhook | 9000 | **9000** | Прием сигналов синхронизации от Forgejo. |
| Dashy | 8080 | **10000** | Web UI дашборда. |
| Memos | 5230 | **10004** | Web UI и API заметок. |
| LinkStack | 80* | **10002** | Web UI (HTTP). |

*\*Примечание: Приложение LinkStack внутри контейнера привязано к порту 80. Для разрешения привязки к привилегированному порту от имени обычного пользователя внутри сетевого пространства контейнера (Namespace) применяется параметр `Sysctl=net.ipv4.ip_unprivileged_port_start=80`.*

## 3. Модель доставки конфигураций (GitOps)

Управление состоянием серверов осуществляется по Pull-модели.

1.  Все изменения в конфигурационных файлах (Systemd Quadlets) фиксируются в репозитории `homelab-deploy`.
2.  При выполнении коммита (Push) центральный Git-сервер (Forgejo) отправляет POST-запрос на порт `9000` целевой ВМ (`obshaga` или `panelka`).
3.  Сервис `webhook` на целевой ВМ верифицирует криптографическую подпись запроса.
4.  В случае успешной верификации локальный агент выполняет `sparse-checkout` (скачивание только директории, относящейся к данному серверу), обновляет файлы `.container` и отдает команду Podman на применение изменений.

Подробное описание работы механизма синхронизации описано в файле `03-gitops-агент.md`.
