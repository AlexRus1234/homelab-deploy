# `services/` — декларации инстансов Incus на skld00

Один файл на сервис: `<имя>.yaml`. Имя файла = имя инстанса (`vl1.yaml` → инстанс `vl1`).
Файл — это **нативный YAML инстанса Incus** (тот же формат, что принимает
`incus create <образ> <имя> < файл.yaml`) плюс политика в `user.*`-ключах и провижининг
в `cloud-init.user-data`. Обоснование схемы целиком — `lxc-build/актуальная схема.md`.

Эталоны — `vl1.yaml` (VictoriaLogs) и `vm1.yaml` (VictoriaMetrics). Читать их как образцы,
здесь — только правила.

## Ключи `user.*`, которые читает хостовый контур

| Ключ | Смысл |
| :--- | :--- |
| `user.managed-by` | маркер контура (`homelab-deploy/skld00`): инстанс без него контур не трогает и не снимает — у Incus инстансы лежат в одном пространстве имён, и без маркера легко задеть чужое |
| `user.role` | роль сервиса (человекочитаемо, для отчётов) |
| `user.package` | имя пакета из личного rpm-md (`-loc`-суффикс — у наших сборок) |
| `user.update_policy` | `inplace` (данные сохраняем, меняются версии пакетов) или `recreate` |
| `user.rollback_window` | сколько живут снапшоты после обновления (базово `24h`) |
| `user.boot_marker` | файл-доказательство, что инстанс прошёл загрузку (`/run/lxc-boot-ok`) |
| `user.healthcheck` | одна строка пробы: ненулевой код = инстанс нездоров |
| `user.data_dataset` | датасет хоста с данными (`tank/vl-data`) |
| `user.data_mountpoint` | куда он монтируется внутри (`/var/lib/victorialogs-loc`) |
| `user.service_user` | имя пользователя сервиса, если оно **не** совпадает с именем пакета (у наших `-loc`-пакетов совпадает, поэтому ключа в декларациях нет) |

Скалярные ключи `config:` контур применяет живьём (`incus config set`). Всё остальное — состав
(`devices`, `cloud-init.user-data`, при необходимости `raw.idmap`) — живьём не меняется: правка
означает **пересоздание инстанса** (см. «Пересоздание»), а не правку молча.

**uid сервиса в декларации не задаётся.** Номер, который выдала система, контур читает из инстанса
(`incus-loc exec <имя> -- id -u <пользователь>`) и от него считает владельца данных на хосте.
Почему его нельзя объявить — в разделе «Откуда взялось правило».

## Данные: датасет хоста, а не том внутри пула Incus

Тома внутри пула (`tank/incus/volumes/...`) под данные БД не создаём: **у zfs-драйвера нет ключа
`source`** (проверено по списку ключей тома: `block.*`, `initial.*`, `security.*`, `size`, `zfs.*`),
то есть подключить существующий датасет томом Incus нельзя, а складывать БД в пул образов —
смешивать разные вещи. Поэтому:

- датасет создаёт владелец, заранее и с нужными свойствами:

```sh
# VictoriaMetrics — метрики: мелкие случайные записи, малый блок
sudo zfs create -o recordsize=16K -o special_small_blocks=0 tank/vm-data

# VictoriaLogs — логи: записи крупнее, блок больше
sudo zfs create -o recordsize=128K -o special_small_blocks=0 tank/vl-data
```

- в декларацию он попадает устройством (обычный путь хоста, без ключа `shift`):

```yaml
devices:
  data:
    type: disk
    source: /tank/vl-data            # путь датасета на хосте
    path: /var/lib/victorialogs-loc  # точка монтирования внутри инстанса
```

- владельцем корня датасета на хосте должен быть **хостовая сторона uid сервиса** — `100000+uid`
  (см. следующий раздел), иначе unprivileged-инстанс видит его как `nobody` и писать не может;
- снапшоты и откат данных контур делает по `zfs snapshot tank/vl-data@...`: датасет снаружи
  инстанса, поэтому переживает recreate.

## Сеть: два macvlan-плеча на картах узла

Инстанс подключается к сети не через бридж Incus, а двумя macvlan-устройствами на физических картах
skld00. Причина — адреса: сервисам нужны адреса в LAN и на P2P-линке, а не в подсети бриджа
(`10.108.54.0/24` из `172.20.0.0/16` не маршрутизируется). Бридж при этом требовал бы перенести
адрес хоста `172.20.50.1` с `enp7s0` на бридж и снести четыре хостовых macvlan-сервиса
(`mv-pg`/`mv-mongo`/`mv-redis`/`mv-s3`): ядро отказывает забирать в бридж интерфейс, у которого есть
macvlan-дети (`RTNETLINK answers: Device or resource busy` — замерено).

```yaml
devices:
  eth0:                       # LAN
    type: nic
    nictype: macvlan
    parent: enp7s0
    name: eth0                # имя важно: гость подхватывает запёкшийся eth0.network (DHCP)
    hwaddr: "02:76:6c:00:00:01"
  eth1:                       # прямой линк skld00 <-> yadr01
    type: nic
    nictype: macvlan
    parent: enp8s0
    name: eth1
    hwaddr: "02:76:6c:01:00:01"
```

Что здесь важно по фактам (всё замерено на живом Incus 2026-10-13):

| Факт | Как проверено |
| :--- | :--- |
| macvlan **не принимает адрес** в декларации: `ipv4.address` — `Invalid device option` | попытка добавить устройство с этим ключом |
| `host_name` для macvlan тоже не существует как ключ | то же |
| `hwaddr` и `name` принимаются | устройство добавилось и поднялось |
| Устройство инстанса с именем `eth0` **перебивает** профильное (`default`) — внутреннего бриджа у сервиса не остаётся | в инстансе один `eth0`, и он macvlan |
| LAN-плечо получает адрес **по DHCP без единого файла в декларации** — по запёкшемуся `eth0.network` (`DHCP=ipv4` + `ClientIdentifier=mac`) | инстанс получил `172.20.255.158/16`, шлюз `172.20.0.1` |
| Линк поднимается статикой из файла в `user-data` (`networkctl reload` + `reconfigure eth1`) | адрес `10.99.99.5/24` появился после reconfigure |
| macvlan-линк Incus создаёт **внутри сетевого неймспейса инстанса** — в `ip link` хоста его нет | в хостовом неймспейсе macvlan-устройств не появилось |

**Проверено на узле 2026-10-13 (боевой прогон).** Обa инстанса пересозданы из деклараций, адреса пришли как
задумано: `vl1` — `172.20.50.101` (LAN, резервация по MAC `02:76:6c:00:00:01`), `vm1` —
`172.20.50.100` (резервация по MAC `02:76:6d:00:00:02`); на линке `172.21.6.101` / `172.21.6.102`.
Проверка **с другого узла** (`172.20.6.10`): ping отвечает, `ip neigh` показывает ровно объявленные MAC,
`http://<LAN-адрес>:9428/health` и `:8428/health` → HTTP 200. Именно это и было целью перехода: раньше
инстансы жили в `10.108.54.0/24` и с других узлов были недостижимы.

Дополнительно (тот же день): **линк проверен с дальней стороны** — с `yadr01` (`172.21.6.250`, интерфейс
`vmbr1`) оба адреса пингуются с 0% потерь за 0.1–0.3 мс, `curl http://172.21.6.101:9428/health` и
`http://172.21.6.102:8428/health` → `OK`, в `ip neigh` на дальней стороне MAC совпадают с декларацией.
На узле также подтверждено: оба живых инстанса несут маркер `user.managed-by: homelab-deploy/skld00`
(без него не работает снятие по удалённой декларации), датасеты `tank/vl-data` и `tank/vm-data`
принадлежат `100478` и в них пишутся данные.

Известное ограничение (observed, не баг): в проекцию состава попадают **комментарии и шапка файла**, поэтому
правка комментария в декларации тоже вызывает пересоздание. Лечится тем, что комментарии исключаются из
проекции; пока это не сделано — правки текста в декларации лучше совмещать с содержательной правкой.

**Адрес LAN задаётся не декларацией, а резервацией DHCP по MAC:** MAC — константа в устройстве,
поэтому пересоздание инстанса адрес не меняет, а смена адреса не требует recreate. До резервации
инстанс получает адрес из пула роутера (`.255.x`). Соглашение по MAC: локально-администрируемый
префикс + читаемое имя сервиса (`76 6c` = «vl», `76 6d` = «vm»), четвёртый байт — номер интерфейса.
Хостовые дети `mv-*` живут в своём диапазоне (`02:17:22:05:00:…`), пересечений нет.

Два свойства, о которых надо помнить:

- **хост и его инстансы по одному родительскому интерфейсу друг друга не видят** (документация Incus).
  Пробы контура это не задевает (они идут через `incus exec`), но «постучать с NAS в `172.20.50.101`» —
  не выйдет; с любого другого узла и с роутера — выйдет;
- **`172.21` — без DHCP**: на линке сервера нет, поэтому адрес там статикой (и потому его смена —
  правка состава → recreate; для линка это редкое событие).

## Правило id-маппинга (дефолт узла: хостовая сторона = `100000+uid`)

**Что выбрано по умолчанию.** Никаких пар `raw.idmap` и никакого `shift`: остаётся штатный маппинг
контейнера, а данные просто принадлежат его хостовой стороне. Контур вычисляет номер сам из живой
карты инстанса и выставляет владельца перед запуском.

| Вариант | Host-предпосылки | Владелец на диске | Отказ при нарушении предпосылки |
| :--- | :--- | :--- | :--- |
| **`100000+uid` — дефолт** | нет: номер берётся из уже разрешённого диапазона `/etc/subuid` | `100479` — «сдвинутый», хостовые скрипты обязаны это знать | нет предусловия |
| `raw.idmap: both <uid> <uid>` | `/etc/subuid` и `/etc/subgid` должны покрывать **сам номер** (он ниже базового диапазона) | `479` — читаемо (`ls`, `zfs send`, инспекция) | старт падает: `forklxc … exit status 1`, инстанс остаётся `STOPPED` |
| `shift: "true"` на устройстве | ядро и файловая система с idmapped mounts (ключ делает оверлей на монтировании) | `100479` | старт падает, если хост/ФС не умеют |
| том Incus в пуле | нет | `100479`, данные внутри `tank/incus/volumes/…` | — |

Почему дефолт именно такой: у нас датасеты приватные для одного сервиса и `chown` нам доступен, а
`shift`/`raw.idmap` существуют для случая, когда источник **нельзя** переприсвоить (например,
домашний каталог настоящего пользователя — так это и описано в FAQ Incus: «make sure that the user
in the container has working read/write permissions», иначе всё видно как `65536:65536`). Плата за
дефолт одна и косметическая — номер на диске нечитаемый.

Что верно при всех вариантах: **root внутри контейнера — это uid 100000 на хосте, не 0**.

### Как считается номер (проверено на живом Incus 2026-10-13)

```
карта инстанса:  volatile.idmap.next = [{"Isuid":true,"Isgid":false,"Hostid":100000,"Nsid":0,"Maprange":65536}, …]
хостовая сторона = Hostid + uid − Nsid      # uid читается из инстанса (id -u <пользователь>)
                                            # пример: 100000 + 479 − 0 = 100479
```

`volatile.idmap.base` для этого **не годится**: там лежит `0` (сторона пространства имён), и
владельцем получилось бы `479` — то есть «сервис молча не может писать». Карта выделяется **при
создании** инстанса, поэтому порядок в контуре: `incus-loc create` → вычислить владельца и `chown`
датасета → `incus-loc start` → ждать cloud-init → health-gate.

Что проверено на живых инстансах (unprivileged, каталог хоста как disk-устройство):

| Проверка | Результат |
| :--- | :--- |
| Каталог на хосте принадлежит `100479`, внутри читаем `stat` | `479:479` |
| Запись внутри под uid 479 | проходит |
| Что получилось на хосте после записи | `100479:100479` |
| Контроль: владелец на хосте `479` (без сдвига) | внутри `65534:65534`, запись под 479 — отказ |

Проверки перед созданием инстанса (для дефолта): только свободность внутреннего номера —
`getent passwd <uid>`. Если сознательно берёшь `raw.idmap`-пару, дополнительно нужно покрытие
`/etc/subuid`:

```sh
grep -E '^root:' /etc/subuid /etc/subgid              # для raw.idmap: номер должен быть разрешён
# если не покрыт: sudo usermod --add-subuids <uid>-<uid> --add-subgids <uid>-<uid> root
```

**Измерено на узле (2026-10-13):** `/etc/subuid` там несёт только `root:100000:65536` — базовый
диапазон контейнеров. Пара `478↔478`/`479↔479` в него не входила, и это давало ровно тот отказ из
таблицы выше (инстансы создавались, но оставались `STOPPED`). Именно поэтому дефолт переведён на
хостовую сторону — там предпосылок нет вовсе.

### Порядок и почему он такой

```
incus-loc create <база> <имя> < декларация     # карта uid выделяется уже здесь
incus-loc start  <имя>                         # cloud-init ставит пакет и создаёт пользователя
incus-loc exec   <имя> -- id -u <пользователь> # фактический uid сервиса
chown 100000+uid <точка монтирования датасета> # ХОСТ, до первого запуска сервиса
incus-loc exec   <имя> -- systemctl start <пакет>.service
проба из user.healthcheck
```

- **карта uid выделяется при `create`** — раньше `chown` невозможен: нечего считать;
- **внутри контейнера `chown` примонтированного датасета невозможен**: он принадлежит неназначенному
  uid, прав на него у root'а контейнера нет. Поэтому владельца ставит хост;
- **сервис стартует после `chown`**, чтобы первый же запуск имел доступ к данным. Отсюда требование
  к `user-data`: он НЕ запускает сервис и НЕ проверяет живость (до `chown` это гарантированно не
  сработает) — его задача пакет, `rpm -q` и `systemctl enable`;
- на `tmpfiles.d` из пакета рассчитывать нельзя: у наших `-loc`-пакетов нет `%post`-скриптлетов, а
  `systemd-tmpfiles-setup` отрабатывает до установки пакета — применение отложилось бы до второй
  загрузки.

### Откуда взялось правило (замерено, а не предположено)

Сначала uid сервиса объявлялся в `user-data` (пин через `systemd-sysusers` с явным номером). На
живом узле это дало:

```
Creating group 'victorialogs-loc' with GID 478.
Suggested user ID 479 for victorialogs-loc already used.
Creating user 'victorialogs-loc' (…) with UID 478 and GID 478.
```

Система выдала `478`, а жёсткая проверка на `479` уронила `runcmd` → `scripts_user` failed →
cloud-init `error`, `cloud-final.service` failed, systemd degraded, проба не прошла. Отсюда два
вывода: номер надо читать у факта (порядок выше), и пару `raw.idmap` с правкой `/etc/subuid` не
использовать (на узле в `/etc/subuid` только `root:100000:65536`, и пара `479↔479` роняла старт
контейнера).

Если когда-нибудь понадобится читаемый номер на диске — берётся `raw.idmap`-пара (тогда сверху
добавляется покрытие `subuid`), либо парковый вариант «номер из зарезервированного блока»
(`both 2479 479`, блок 2400–2999 за сервисами узла). Как и в Proxmox, где по умолчанию сдвигается
весь контейнер, а для bind-mount'а документация предлагает `lxc.idmap` с парой «один в один».

## Отладочный этап: первый запуск руками, автоматика выключена

Пока на узле есть файл-выключатель `/etc/lxc-automation.off`, `reconcile.sh` **ничего не меняет** —
только печатает, что сделал бы. Владелец снимает флаг, когда захочет включить автоматику целиком.

Ручной прогон (ровно то, что потом сделает контур; `sudo` — потому что Incus и ZFS рутовые):

```sh
# 0. автоматика выключена, чтобы не вмешалась; датасет существует
sudo touch /etc/lxc-automation.off
zfs list tank/vl-data

# 1. создать и запустить: cloud-init поставит пакет и включит юнит
sudo incus-loc create leap16-base vl1 < /opt/appdata/git-repo/servers/skld00/services/vl1.yaml
sudo incus-loc start vl1
sudo incus-loc exec vl1 -- cloud-init status --wait

# 2. фактический uid сервиса и карта инстанса
sudo incus-loc exec vl1 -- id -u victorialogs-loc
sudo incus-loc config get vl1 volatile.idmap.next      # Hostid=100000

# 3. владелец данных — хостовая сторона этого uid (для 479 это 100479)
sudo chown 100479:100479 /tank/vl-data

# 4. запуск сервиса и проба — то же делает контур
sudo incus-loc exec vl1 -- systemctl start victorialogs-loc.service
sudo incus-loc exec vl1 -- test -f /run/lxc-boot-ok && echo "загрузка пройдена"
sudo incus-loc exec vl1 -- /usr/local/sbin/lxc-healthcheck \
  --command "$(sudo incus-loc config get vl1 user.healthcheck)"

# 5. снаружи
curl -fsS "http://$(sudo incus-loc list vl1 -c4 --format csv | cut -d' ' -f1):9428/health"

# 6. переделать
sudo incus-loc delete vl1 --force
```

## Что делает автоматика после включения

| Ситуация | Действие |
| :--- | :--- |
| инстанса нет | `create` → `start` → `cloud-init status --wait` → читает uid из инстанса → `chown 100000+uid` датасета → `systemctl start` юнита → health-gate |
| инстанс есть | на каждом прогоне читает uid, проверяет владельца данных; если разъехался — возвращает и перезапускает юнит |
| инстанс есть, разошлись скаляры | `incus-loc config set` по каждому отличающемуся ключу |
| инстанс есть, изменился состав | пересоздаёт: снапшот датасета → старый инстанс отставляет в сторону (`rename`) → `create` по новой декларации → health-gate; при провале — возврат старого инстанса и `zfs rollback` |
| инстанс есть, записи о применении нет | прогоняет health-gate: если проба не прошла — «провал» с подсказкой снести и создать заново |
| создан, но пробу не прошёл | пишет «провал» в статус, выкладывает хвост `cloud-init-output.log` и возвращает ненулевой код — сбой виден в логе хука |
| декларации нет в git, инстанс есть | снимает: снапшот датасета → `stop` → `delete`. Данные остаются на датасете (он не удаляется); снимается только инстанс с маркером `user.managed-by` |

Отчёт каждого прогона — строки в `/var/lib/lxc-update/status` (имя, действие, результат,
подробности, длительность). Что применено последним — `/var/lib/lxc-update/applied/<имя>`
(два хеша: состав и скаляры).

## Пересоздание (`recreate`): правка состава, обновление, откат

Правка состава (`devices`, `cloud-init.user-data`, `raw.idmap`) применяется только пересозданием:
контур снимает снапшот данных, отставляет работающий инстанс в сторону, собирает новый по новой
декларации и проверяет пробой. Данные при этом не теряются: датасет живёт снаружи инстанса.

```
1. zfs snapshot <ds>@recreate-<дата>                      # данные
2. incus-loc stop <имя> && incus-loc rename <имя> <имя>-pre-<дата>  # старый инстанс НЕ удаляется
3. create по новой декларации → start → cloud-init → uid → chown → systemctl start → health-gate
4. успех:  applied обновлён; <имя>-pre-<дата> живёт до GC (порог тот же: rollback_window / N=3)
   провал: delete нового → rename старого обратно → zfs rollback <ds>@recreate-<дата> → start → проба
```

**Почему откат опирается на инстанс, а не на старую декларацию.** Первая версия плана откатывалась
пересозданием по предыдущей декларации из git. Это ломается ровно там, где откат и нужен: если
обновление подтянуло другую базу или версия пакета уехала из Хражевника, старая декларация уже не
собирается. Поэтому старое состояние держим **как сам инстанс** — `rename` на zfs ничего не копирует,
и в отставленном `<имя>-pre-<дата>` остаются пакеты и конфиги ровно те, что работали. git-декларация
при этом остаётся третьим эшелоном: она бесплатна и может пригодиться, но не она основа отката.

Плата за пересоздание — простой сервиса на время операции (замеры на узле: 30–70 с). Плата за
откат — данные возвращаются к снапшоту, то есть записи, сделанные между снапшотом и откатом,
теряются. Для логов и метрик это приемлемо; для сервиса с транзакционными данными так делать
нельзя без отдельного решения.

Ручной режим — когда декларация не менялась, а инстанс надо пересобрать с нуля (например, он
остался в отлаженном «полуфабрикате»):

```sh
sudo /opt/appdata/git-repo/servers/skld00/reconcile.sh --recreate vl1
```

В этом режиме хеши не сравниваются: берётся текущая декларация, остальные сервисы не трогаются.
Откат при провале — тот же.

**Ночной контур обновления — следующий шаг.** Там пересоздание не нужно: инстанс не меняет состав,
меняются версии пакетов (`zypper dup`), поэтому откат делается снапшотом инстанса
(`incus snapshot create` / `incus snapshot restore`), а датасета — `zfs snapshot`. Тот же шаг
добавляет GC отставленных инстансов и снапшотов по `user.rollback_window` с потолком N=3.

## Удаление: декларации нет в git — инстанса нет на узле

Правило то же, что у агента на ВМ (`sync-state.sh`: `git diff --diff-filter=D` + `systemctl stop` +
`rsync --delete`): **декларация исчезла из git — сервис на узле снимается.** Для Incus это отдельная
ветка: «файла нет» само по себе ничего не удаляет, поэтому перебор идёт не по существующим файлам,
а по дельте удалённых.

```
git diff --diff-filter=D <старый> <новый> -- servers/skld00/services/
  для каждого удалённого <имя>.yaml:
    zfs snapshot <датасет>@removed-<дата>     # страховка; сам датасет НЕ удаляется
    incus stop <имя> → incus delete <имя>
```

Три отличия от ВМ, и все — про безопасность:

- **снимается только инстанс с маркером `user.managed-by`.** На ВМ роль «это наше» играет сам путь
  (`~/.config/containers/systemd/`), у Incus инстансы лежат в одном пространстве имён: без маркера
  ветка снятия могла бы удалить чужой инстанс, просто совпавший по имени. Инстанс без маркера
  получает в статусе строку «пропуск», и контур его не трогает;
- **данные не удаляются.** Датасет лежит снаружи инстанса, контур его не трогает; перед снятием
  снимается снапшот `<датасет>@removed-<дата>`, а в отчёте пишется, что датасет осиротел. «Сервис
  больше не нужен» и «данные больше не нужны» — два разных решения, и второе принимает человек;
- **восстановление — обычный git revert + push**: контур создаст инстанс заново из базы по вернувшейся
  декларации, данные на датасете уже на месте.

Ручной прогон (`reconcile.sh` без аргументов) снятием не занимается: без git-хешей неизвестно, что
именно удалили. При выключателе `/etc/lxc-automation.off` снятие, как и всё остальное, только
печатается планом.
